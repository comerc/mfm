# Тестирование сервиса модерации

## Структура тестов

Файл `service_test.go` содержит юнит-тесты для сервиса модерации, использующие сгенерированные mockery моки, табличные тесты и подход `setupMocks`, в соответствии с правилами тестирования проекта.

## Соблюдение правил тестирования

### 1. Использование `assert.AnError`
Вместо создания специфических ошибок с помощью `errors.New()` используются `assert.AnError` для тестирования сценариев с ошибками.

### 2. Именование тестов
Имена тестов соответствуют требованиям:
- `TestModerate_Success` - для публичного метода Moderate (успешный сценарий)
- `TestModerate_Error_*` - для публичного метода Moderate (ошибочные сценарии)
- `Test_getMaxScore` - для приватного метода

### 3. Применение `t.Parallel()`
Все тесты следуют шаблону AAA:
- **Arrange** - подготовка данных и моков
- **Act** - выполнение тестируемого метода
- **Assert** - проверка результатов

### 4. Размещение тестов
Юнит-тесты находятся в том же пакете, что и тестируемый код, с суффиксом `_test.go`.

### 5. Именование тестов
Имена тестов соответствуют требованиям:
- `TestModerate_*` - для публичного метода Moderate
- `Test_getMaxScore` - для приватного метода

### 6. Именование табличных тестов
Имена табличных тестов используют snake_case без пробелов и заглавных букв:
- `single_image_with_low_nsfw_score`
- `single_image_with_high_nsfw_score`
- и другие

### 7. Порядок тестов
Тесты расположены в следующем порядке:
- Тесты для публичного метода `Moderate_*` (сначала `Moderate_Success`)
- Тесты для приватной функции `getMaxScore`

### 8. Использование конструктора сервиса
В тестах используется конструктор `New()` для создания экземпляра сервиса модерации:
```go
service := New(mockMediaReader, mockModelRunner)
```

### 9. Настройка моков
Для настройки моков используется testify/mock API с .EXPECT():
- `mockMediaReader.EXPECT().Read(...).Return(...)` для метода Read
- `mockModelRunner.EXPECT().Infer(...).Return(...)` для метода Infer

## Компоненты тестов

### Сгенерированные моки
- `mocks.MediaReader` - сгенерированный мок для интерфейса `MediaReader`
- `mocks.ModelRunner` - сгенерированный мок для интерфейса `ModelRunner`

Моки были сгенерированы с помощью mockery:
```bash
//go:generate mockery --name=MediaReader
//go:generate mockery --name=ModelRunner
```

### Функция setupMocks
В некоторых тестах используется функция `setupMocks` внутри структуры тестов:
```go
setupMocks: func(*Service) (*mocks.MediaReader, *mocks.ModelRunner)
```

Функция устанавливает моки в сервис и настраивает ожидания с помощью методов моков.

### Табличные тесты
Тесты используют табличную структуру для проверки различных сценариев:
- Успешная модерация (включающая одиночные изображения, несколько изображений, видео, смешанные файлы)
- Обработка ошибок при чтении файлов
- Обработка ошибок при инференсе модели
- Тесты вспомогательных функций

## Покрытие
Тесты обеспечивают покрытие 97.4% кода сервиса модерации, включая все основные ветви логики.

## Особенности реализации
- Все подтесты помечены как `t.Parallel()` для ускорения выполнения
- Используются сгенерированные моки из пакета `mocks`
- Используется `mockMediaReader.On().Return()` и `mockModelRunner.On().Return()` для настройки ожиданий
- Автоматическая проверка ожиданий происходит через `Cleanup` функцию, зарегистрированную в `mocks.NewMediaReader()` и `mocks.NewModelRunner()`
- Для каждого подтеста создаются новые моки, чтобы избежать конфликта ожиданий
- Используется `t.Cleanup()` для освобождения ресурсов (вместо `defer`)
